## ✨ What is AttendX?

**AttendX** eliminates the daily stress of college attendance tracking and timetable management. Built specifically around academic regulations (such as **IIIT Una Academic Regulation 6.1–6.10** mandating 75% attendance to appear for semester examinations), AttendX treats academic attendance not as a static spreadsheet, but as an active **mathematical optimization problem**.

Whether dealing with shifting lecture halls, lab batches, unscheduled extra classes, gazetted holidays, or exam preparation leaves, AttendX forecasts exactly how many lectures you can safely skip, warns you before you enter the debar zone, and automatically synchronizes with classmates via encrypted peer-to-peer data transfers.

## 🧠 Predictive Attendance & Leave Simulation Engine

AttendX treats academic attendance as a dynamic linear inequality.

### 1. Mathematical Formulas
Given:
- $A$: Number of lectures attended so far.
- $H$: Total number of lectures held so far.
- $T$: Target attendance threshold (default: $0.75$, or $75\%$).
- $P$: Current attendance percentage:
  $$P = \left( \frac{A}{H} \right) \times 100$$

#### Case A: Above Target ($P \ge 75\%$) — Safe Bunks Calculation
The maximum number of consecutive upcoming lectures $B$ a student can miss without dropping below $T$ is:
$$\frac{A}{H + B} \ge T \implies B = \left\lfloor \frac{A - (T \times H)}{T} \right\rfloor$$
*Example:* If $A = 30$ and $H = 36$ ($83.33\%$), then:
$$B = \left\lfloor \frac{30 - (0.75 \times 36)}{0.75} \right\rfloor = \left\lfloor \frac{30 - 27}{0.75} \right\rfloor = 4\text{ safe bunks}$$

#### Case B: Below Target ($P < 75\%$) — Recovery Requirement
The minimum number of consecutive upcoming lectures $C$ a student must attend to restore their percentage to $T$ is:
$$\frac{A + C}{H + C} \ge T \implies C = \left\lceil \frac{(T \times H) - A}{1 - T} \right\rceil$$
*Example:* If $A = 20$ and $H = 32$ ($62.5\%$), then:
$$C = \left\lceil \frac{(0.75 \times 32) - 20}{1 - 0.75} \right\rceil = \left\lceil \frac{24 - 20}{0.25} \right\rceil = 16\text{ consecutive classes}$$

### 2. Multi-Day Calendar Simulation (`computeMultiDaySimulationBlock`)
When planning extended leave (e.g., attending a hackathon or going home for a festival), AttendX maps the student's actual timetable slots against the academic calendar:
1. Traverses future dates from the leave start date to the leave end date.
2. Filters out official institutional holidays and Sundays.
3. Sums up all scheduled lectures for each subject during that window.
4. Computes exact projected percentage:
   $$P_{\text{projected}} = \frac{A}{H_{\text{current}} + H_{\text{missed}}} \times 100$$
5. Alerts the user if the planned absence triggers an irreversible debarment.

## 🚀 Over-The-Air (OTA) Release Pipeline

AttendX avoids Google Play Store update delays (which take days to approve) by streaming atomic frontend updates directly to client devices via **`@capgo/capacitor-updater`**.

```mermaid
flowchart TD
    A["Developer commits web changes"] --> B["npm run build (Vite + Rolldown)"]
    B --> C["node zip_dist.cjs bundles client/dist into update.zip"]
    C --> D["server/src/uploads/update.zip uploaded to backend"]
    D --> E["Mobile App boots (Capacitor WebView)"]
    E --> F["GET /api/system/update?t=timestamp"]
    F --> G{"localVersion < latestVersion?"}
    G -- No --> H["Serve local assets instantly (0ms)"]
    G -- Yes --> I["CapacitorUpdater downloads update.zip in background"]
    I --> J["Extracts into sandbox & verifies integrity"]
    J --> K["Seamlessly reloads WebView to latest version"]
```

- **Rollback Safety**: If the newly downloaded bundle crashes on launch, Capacitor automatically rolls back to the previous stable bundle.
- **Downgrade Loop Guard**: `localVersion` and `latestVersion` are synchronized to prevent redundant asset downloads.

## 🔔 Local Notifications, Alarms & Do Not Disturb (DND)

### 1. Timetable Alarms (`NotificationService.ts`)
AttendX schedules device alarms using `@capacitor/local-notifications`, fully operational offline:
- **Pre-Class Reminders**: Dispatched **5, 10, or 15 minutes** before scheduled lecture start times with classroom number.
- **Next-Class Heads-Up**: Alerts the student when their current lecture finishes, previewing what room to walk to next.
- **End-of-Day Summary**: Dispatched on the conclusion of the day's final lecture (*"You are done for the day! Overall attendance: 82%"*).
- **Birthday Greetings**: Automated notification scheduled for 9:00 AM on the student's birthday.

### 2. Native Do Not Disturb (DND) Auto-Ringer (`ringer.ts`)
During lecture hours, ringing phones interrupt classrooms. AttendX interfaces directly with the Android hardware audio manager:
1. Requests Android `ACCESS_NOTIFICATION_POLICY` permission.
2. When a lecture begins, AttendX automatically toggles the phone ringer to **Vibrate / Silent**.
3. When the scheduled lecture period expires, AttendX restores the student's previous ringer mode.

## 🔐 Linked Devices & Passive Session Security

AttendX enforces multi-device session management inspired by modern banking security standards:

- **Token Rotation**: Every login issues an ephemeral `AccessToken` (15m expiry) and a cryptographically secure `RefreshToken` stored in PostgreSQL and cached in Redis.
- **Linked Devices Dashboard**: Under **Settings › Linked Devices**, students can view all active sessions, including device type (Android, Windows, macOS, Linux), browser, IP address, and last active timestamp.
- **Remote Revocation**: Students can remotely sign out individual devices or trigger a global session purge.
- **Passive Garbage Collection (`autoTerminateMonths`)**: Sessions inactive beyond 1, 3, or 6 months are automatically pruned during database read cycles, preventing database bloat.

## ⚡ Zustand Offline-First Global State Architecture

AttendX works completely offline. All network queries are cached locally using **Zustand** backed by **CapacitorPreferences**:

```mermaid
flowchart TD
    subgraph Zustand Store Architecture
        A["authStore<br/>User Profile & Session Tokens"]
        B["attendanceStore<br/>Active Semester, Subjects, Agendas & Logs"]
        C["offlineStore<br/>Offline Mutation Queue & Rollback Engine"]
        D["cacheStore<br/>L1 Memory SWR Cache (0ms Hydration)"]
        E["syncStore<br/>P2P 6-Digit Transfer Code & TTL State"]
        F["notificationStore<br/>Reminder Lead Times, DND & Location Flags"]
    end
```

- **Optimistic UI Execution**: Marking attendance, adding extra lectures, or deleting events updates the UI in **`0ms`** with local rollback if network requests fail.
- **Offline Mutation Queue**: Actions performed in classrooms without internet are queued in `offlineStore` and automatically replayed in order upon reconnection.
- **Stale-While-Revalidate (SWR)**: L1 cached data displays on frame 0, eliminating loading spinners during app launch.

## 📊 Engineering-Grade Scalability Breakdown

AttendX is engineered to operate on a **100% Free-Tier Architecture** while serving an entire university department.

### Executive Scalability Summary

| Metric | Free Tier Capacity | Primary Limiting Constraint |
| :--- | :--- | :--- |
| **Total Registered Users** | **8,000 – 12,000 students** | Neon 500 MB database storage limit |
| **Daily Active Users (DAU)** | **800 – 1,500 DAU** | Render 0.1 shared vCPU & event loop |
| **Peak Concurrent Users** | **80 – 150 concurrent** | Render 512 MB RAM & burst capacity |
| **AI Copilot Throughput** | **100 – 150 queries/minute** | Gemini 15 RPM (mitigated by fast-path) |
| **Active Session Cache** | **~15,000 sessions** | Redis 30 MB key-value memory limit |

---

### 1. Database Tier: Neon Serverless PostgreSQL (500 MB Storage)

Neon grants **500 MB** of persistent storage with pooled connections via PgBouncer.

#### Per-User Storage Footprint:
- **User Account & Preferences**: `User`, `NotificationPreferences` $\approx$ `1.2 KB`
- **Subjects & Weekly Timetable**: 6–8 subjects with 30–40 weekly slots $\approx$ `7.5 KB`
- **Daily Attendance Logs**: 90 semester teaching days $\times$ 4 lectures/day = 360 rows $\approx$ `36 KB`
- **Assignments, Milestones & Events**: Submissions, exams, remarks $\approx$ `8 KB`
- **B-Tree Indexes & PostgreSQL Page Overhead**: $\approx 30\%$ overhead $\approx$ `16 KB`
- **Total Footprint per Student per Semester**: **$\approx 65\text{–}70\text{ KB}$**

$$\text{Total Student Capacity} = \frac{500\text{ MB} \times 1024\text{ KB/MB}}{70\text{ KB/student}} \approx \mathbf{7,300\text{ – }12,000\text{ registered accounts}}$$

> [!NOTE]
> Currently, AttendX actively serves **200+ students** at IIIT Una, consuming less than **15 MB** (<3%) of Neon's database storage.

---

### 2. Compute Tier: Render Web Service (512 MB RAM, 0.1 vCPU)

#### Memory Budget (512 MB Limit):
- Node.js runtime + Express base RSS: `~75 MB`
- Prisma ORM client & query buffers: `~45 MB`
- In-memory route handling buffers under concurrency: `~60 MB`
- **Total Working Memory Under Active Load**: **`~180 MB – 220 MB`**
- **Headroom**: **`~290 MB` of spare RAM**, preventing Out-Of-Memory (OOM) crashes.

#### Throughput:
- Lightweight read/write requests (fetch timetable, toggle attendance mark) execute in `120 – 180 req/sec`.
- During peak class start times (e.g. 8:50 AM – 9:10 AM), 100 students opening the app simultaneously resolve within `400–600ms`.

---

### 3. Caching Tier: Redis Free Instance (30 MB Memory)

- **Cached Session Token / User Context**: `~1.2 KB` per active user.
- **Attendance Digest & Subject Matrix**: `~1.8 KB` per user.
- **Capacity**:
  $$\frac{30\text{ MB} \times 1024\text{ KB/MB}}{2\text{ KB/user}} \approx \mathbf{15,360\text{ active cached sessions}}$$
- Under 1,000 Daily Active Users, Redis consumes less than **10–12 MB** with automated TTL eviction.

---

### 4. AI Copilot: Gemini 3.8 Flash (15 RPM Free Tier Optimization)

The free Gemini API key enforces a strict quota: **15 Requests Per Minute (RPM)**. 

#### Fast-Path Routing Efficiency:
Our 3-tier router handles:
1. **Greetings / Small Talk**: Resolved in `< 2ms` (0 Gemini RPM).
2. **Attendance Actions ("Mark Math present with remark sick")**: Resolved in `< 5ms` (0 Gemini RPM).
3. **Weekly / Monthly Report Triggers**: Resolved in `< 4ms` (0 Gemini RPM).
4. **Timetable / Upcoming Classes Lookups**: Resolved in `< 10ms` (0 Gemini RPM).

$$\frac{15\text{ Gemini RPM}}{0.12\text{ miss rate}} \approx \mathbf{125\text{ user AI queries per minute}}$$

This allows **85–90%** of all student queries to resolve with zero API quota consumption.

## 💻 Local Development Setup

### Prerequisites
- **Node.js**: `v20.0.0` or higher
- **PostgreSQL**: Local instance or free Neon connection string
- **Redis**: Local instance or cloud Redis URL

### 1. Clone the Repository
```bash
git clone https://github.com/nrai18/AttendX.git
cd AttendX
```

### 2. Install Dependencies
```bash
# Install backend dependencies
cd server
npm install

# Install frontend dependencies
cd ../client
npm install
```

### 3. Environment Variables
Create a `.env` file in the `server` directory:
```env
PORT=3000
DATABASE_URL="postgresql://user:password@localhost:5432/attendx?sslmode=require"
REDIS_URL="redis://localhost:6379"
JWT_SECRET="your_jwt_secret"
JWT_REFRESH_SECRET="your_jwt_refresh_secret"
GEMINI_API_KEY="your_gemini_api_key"
RESEND_API_KEY="your_resend_api_key"
ELEVENLABS_API_KEY="your_elevenlabs_api_key"
PUBLIC_APP_URL="https://attendx.tech"
```

### 4. Initialize Database
```bash
cd server
npx prisma db push
```

### 5. Run Development Servers
```bash
# Terminal 1: Backend
cd server
npm run dev

# Terminal 2: Frontend
cd client
npm run dev
```

### 6. Build Android APK
```bash
cd client
npm run build
npx cap sync android
cd android
./gradlew assembleDebug
```
The resulting APK will be compiled at `client/android/app/build/outputs/apk/debug/app-debug.apk`.
